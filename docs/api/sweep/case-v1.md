## Items considered for promotion and rejected

- **Per-field default sort direction for `order_by=indexed_on` /
  `order_by=server_date_modified`** ("defaults to the oldest ... date"):
  confirmed in `SimpleSortableResourceMixin.apply_sorting`
  (`corehq/apps/api/resources/__init__.py`) that omitting the `-` prefix
  sorts ascending (oldest first) — this is the standard meaning of "prefix
  with `-` to reverse" already in the spec's `order_by` description, not a
  distinct fact needing its own sentence.
- **Undocumented parameter aliases `case_name`, `case_type`, `type.exact`,
  `name.exact`, `external_id.exact`, `contact_phone_number`**: found while
  reading `case_param_consumers` in `corehq/apps/api/es.py` — these GET
  param names are recognized by dedicated (sometimes "analyzed") filter
  logic, separately from the documented `name`, `type`, `external_id`
  params (which fall through to a generic lowercased term filter on the
  same underlying ES fields and work correctly). Neither the old page nor
  the spec ever claimed anything about these aliases, so there is no
  inaccurate prose to fix and no page content to reduce here — adding
  brand-new parameter documentation the page never had is outside this
  sweep's scope (verifying and reducing existing claims), so left alone.
- **`owner_id`/`user_id` "should not be used together" as an enforced
  rule**: checked `es_query_from_get_params` — neither is validated as
  mutually exclusive; both simply add independent term filters if both are
  present. The existing spec wording is advisory ("should not be used
  together with"), not a claim of enforcement, so it already matches
  actual behavior and needs no correction.
